## Дерево решений и прямые ответы пользователя

- Цель, ранее заданная кейсом: универсальный агент для публичных и неизвестных задач; одна лишь перепись исходников не считается улучшением.
  - Q1: **до 15 минут на одну новую локальную гипотезу**.
  - Q2: **предобработка выбирается по данным и модели**; обязательное Gaussian-преобразование/удаление выбросов снято.
  - Q3: **дополнительное заранее фиксированное сравнение финалистов**; явно разрешён один сравнительный запуск текущего лидера на этом новом протоколе. Старые поиски и конфигурации на прежнем протоколе повторно не запускать.
  - Q4/Q5: без просадки достаточно подтверждённого улучшения; при компромиссе нужен относительный выигрыш **строго >15%** и ухудшение другой метрики **строго <10%**.
    - Regression gain = (RMSE_control − RMSE_new) / RMSE_control.
    - Classification gain = (F1_new − F1_control) / F1_control.
    - Проценты относительные, не процентные пункты. Контроль на новом разбиении измеряется заново; старые значения другого split не подставляются.

## Конкретный план для итогового согласования

1. Зафиксировать SPEC010 и план до реализации. Писать отдельный агент без выбора по SHA публичных датасетов; прежний лидер и архив сохранить как контроль. Не копировать обязательную full-v1 политику.
2. Ввести цикл «диагностика → предположение о причине → один новый механизм → измерение». Диагностику для выбора гипотез получать из training-only inner-прогнозов; финальный дополнительный holdout не передавать LLM и не использовать для подбора.
3. Первая короткая серия: **H52** (классификация по смешанному расстоянию) и **H62** (регрессия с низкоранговыми взаимодействиями в исходной шкале). Оба механизма ещё не проверены; они могут проиграть. Параметры, данные, split, source и лимит 900 секунд фиксировать до fit; сверить полный журнал перед каждым запуском. Не менять карточки задним числом.
4. H61 не запускать автоматически: соседнее сглаживание имеет основание только после train-only диагностики противоречивых локальных меток. Слабый редкий класс сам по себе не означает шумную разметку. Focal loss также не выбирать только из-за дисбаланса.
5. Выбрать финалиста внутри research/train, затем один раз сравнить с текущим лидером на дополнительном заранее зафиксированном протоколе с учётом времени/групп. Это проверка устойчивости на исходных публичных данных, а не независимая private-оценка.
6. Применить согласованное правило выигрыша к сравнимым измерениям. Публиковать новый ZIP только при выполнении правила и платформенного preflight; иначе сохранить отрицательные результаты и текущий архив, не обещать улучшения.
