# Архитектура AutoResearch агента

Обновлено: 2026-10-23. Описание относится к текущим файлам `solution.py` и `automl_*.py`; результаты предыдущих сборок отмечены отдельно в [VALIDATION.md](VALIDATION.md).

## Поток запуска

`solution.py task.md` ограничивает число CPU-потоков, фиксирует время старта и передаёт задачу в `automl_engine.main`. Engine сначала разбирает контракт задачи, строит baseline submission и проверяет его до запуска обучения. Затем подготавливает фиксированные search и outer audit split, профиль только по fit-части и изолированно запускает worker для каждого кандидата.

Поиск использует nested-разбиение, если данных хватает: внутренний split задаёт search score, а внешний holdout остаётся недоступным для предложений. После остановки предложений engine замораживает baseline и search winner, оценивает оба на одном outer holdout и записывает парные диагностические результаты. Audit не выбирает модель: final full fit всегда получает search winner. Если он совпадает с baseline, на audit оценивается один кандидат. При недостатке времени или невозможном nested split audit пропускается или помечается недоступным.

## Модули

- `automl_data.py` разрешает train/test/sample и optional dictionary из `task.md`, schema и файлов; определяет target, ID, metric, classes и group; задаёт split, scoring и проверку submission. `X_test` выровнен по ID в порядке sample.
- `automl_models.py` валидирует и канонизирует кандидатов, строит ограниченный каталог моделей, обучаемые преобразования и Python-признаки из DSL.
- `automl_engine.py` управляет дедлайном, split-ами, baseline/кандидатами, дедупликацией, обратной связью LLM и публикацией безопасной submission.
- `automl_worker.py` обучает одну модель в дочернем процессе, рассчитывает выбранную метрику на заданном split, формирует диагностику, предсказания и candidate submission.
- `automl_llm.py` при наличии настроек обращается к OpenAI-compatible endpoint и принимает одну структурированную proposal; иначе поиск использует offline policies.
- `automl_runtime.py` ограничивает время и память процесса, число потоков и передаваемое worker/API окружение; прерывает всё дерево дочерних процессов при timeout.

## Предложения и безопасный DSL

Ключ кандидата — SHA256 canonical JSON после нормализации параметров; свободный текст `hypothesis` исключён из ключа. Поэтому смена формулировки не позволяет повторить уже проверенную конфигурацию. Дубликаты пропускаются, счётчик и причина сохраняются в diagnostics. Неприемлемый кандидат получает feedback; попытка с неизвестным feature column завершается ошибкой worker и не заменяет текущую submission.

LLM не передаёт исполняемый Python. Она описывает до 24 операций (`add`, `sub`, `mul`, `div`, `log1p`, `abs`) через имена `left`/`right` колонок. Engine проверяет имена и тип операции, затем компилятор строит код из фиксированного шаблона; неизвестная колонка завершает candidate как failed. Частотные кодировки и другие preprocessing таблицы обучаются только на fit.

## Метрики, лимиты и ранняя submission

Primary metric берётся из task contract; неизвестная или неоднозначная явно указанная метрика приводит к ошибке, а не к скрытой подмене. Scorer поддерживает regression losses/`r2`, варианты F1, accuracy, balanced accuracy, ROC AUC и log loss. Для probability metrics worker выравнивает вероятности по классовому порядку, заданному train, и проверяет конечность, диапазон и сумму.

Дедлайн `AUTOML_TIME_LIMIT` по умолчанию 10 200 секунд и жёстко ограничен сверху 10 200 секундами. `AUTOML_MAX_EXPERIMENTS` по умолчанию 12, с пределом 24; `AUTOML_THREADS` ограничен 1–8. Каждый subprocess получает максимум доступного бюджета, резерв на завершение работы, ограничение вывода и память по умолчанию 28 000 MiB. Для поиска timeout одного опыта дополнительно ограничен 1 200 секундами и частью общего бюджета. LLM запрос ограничен 25 секундами, максимум 8 вызовов, до 3 последовательных неудач и ориентиром 48 000 токенов.

До профилирования и экспериментов создаётся проверенный fallback `submission.csv`. После каждого завершённого улучшения рабочая submission заменяется атомарно; при ошибках, таймауте или нехватке бюджета сохраняется последняя валидная версия. Успех задачи не требует, чтобы каждый эксперимент, audit или final refit завершился: статус и этапы записываются в `agent_runs/<timestamp>/summary.json`.

Worker не получает API credentials. Только отдельный LLM subprocess получает явно заданные `OPENAI_BASE_URL`, `OPENAI_API_KEY`, `OPENAI_MODEL`; ошибки записываются без текста исключения, чтобы не раскрывать URL/секреты. В текущем локальном запуске реальный Qwen API не настроен; проверялись mock HTTP ответы.
