# SPEC-001: универсальный агент для ML-задач

- Статус: Черновик требований по источникам.
- Дата: 2026-10-23, Москва.
- Основание: пользователь предоставил материалы хакатона; [обзор источников](../sources/README.md).
- Согласование: дизайн и план реализации ещё не согласованы.
- План: не создан; документ фиксирует требования, а не выбранную архитектуру.

## Цель и контекст

Создать агента под управлением LLM, который получает описание незнакомой ML-задачи и данные, самостоятельно исследует их, проводит эксперименты и формирует файл предсказаний.
Один и тот же код должен работать на публичных задачах регрессии и классификации и на двух заранее неизвестных приватных задачах без ручной адаптации.
Улучшение фиксированных моделей на двух публичных датасетах само по себе не выполняет эту цель.

## Границы

Входит: понимание условия, данных и метрики; выбор валидации; генерация и запуск кода; обучение; оценка гипотез; память экспериментов; выбор результата; создание корректного submission; упаковка агента.
Не входит: развёртывание обученной модели в production, мониторинг после сдачи, внешние обучающие данные, предобученные ML-модели.
Код решения можно распределить по модулям, но точка входа должна оставаться единой.

## Публичные данные

- Регрессия: 53 308 train-строк, 62 признака, таргет `site_eui`; test — 22 449 строк. Train охватывает Year_Factor 1–5, test — 6.
- Классификация: 87 670 train-строк, 42 признака, таргет `attack_cat`; test — 41 166 строк; 10 несбалансированных классов.
- Каждый набор содержит train, test, словарь признаков и sample_submission. Значения в sample_submission не являются истинными ответами.
- Id — идентификатор строки для ответа; использовать его как глобальный ключ для переноса таргетов между train/test нельзя.
- Точные состав, контрольные суммы и структурные проверки: [manifest](../sources/intake-manifest.json).

## Ограничения организаторов

По PDF, с. 6–8 и 16–19:

- Финальная сдача — ZIP с `solution.py`, выполнение в Docker.
- Лимит — 3 сабмита на команду в сутки, обновление в 00:00 по Москве.
- Разрешённая на отборочном этапе LLM в документе названа Qwen3.8-27B; точное имя `OPENAI_MODEL` берётся из настроек организаторов, а не выводится из этого названия.
- Доступный бюджет LLM на разработку указан как 600 рублей в день на команду; отдельный численный лимит токенов не приведён.
- Интернет из контейнера запрещён; доступ к предоставленному LLM endpoint нужно рассматривать отдельно и проверить.
- Платформа не возвращает промежуточные метрики test; агент использует собственную validation на train.
- Для private-проверки неизменный агент получает две новые задачи через тот же интерфейс; содержимое и метрики заранее неизвестны.

## Оценка по условиям

Формулы сверены визуально по с. 18–19 PDF:

```text
S_reg = 100 * max(0, 1 - RMSE / B_RMSE)
S_cls = 100 * max(0, (MacroF1 - B_F1) / (1 - B_F1))
Score_public = (S_reg + S_cls) / 2
Score_private = (S_1 + S_2) / 2
```

`B_RMSE > 0` и `B_F1 < 1` — метрики платформенного бейзлайна на соответствующем test, их значений в материалах нет.
Локальные контрольные модели команды не являются подтверждённой заменой этих констант.
Поэтому целевой численный score и качество на скрытом test сейчас не установлены.

## Допущения и открытые вопросы

1. Для точки входа принят явно заданный `solution.py` (с. 6), хотя с. 17 упоминает `script.py`; это несоответствие необходимо проверить при подготовке пакета.
2. CSV в ZIP находятся рядом с task.md, а указанные в условиях вложенные пути отсутствуют. Способ локального размещения и поведение при расхождении путей нужно определить в дизайне.
3. `mcp` импортируется baseline, но отсутствует в requirements. Установка дополнительных библиотек не считается разрешённой автоматически; наличие пакета в Docker ещё не проверено.
4. API endpoint, фактическое имя модели и доступность авторизации пока не проверены. Ключи не запрашиваются для хранения в проекте.
5. Архитектура агента, стратегия распределения бюджета и порядок интеграции работы `sergey_branch` ещё не выбраны.
