## HYP-070: temporal entity linking across nuisance location changes

Утверждение: идентификация устойчивого физического профиля с явным отказом при коллизии сохраняет полезную историю, потерянную при изменении ELEVATION; перенос результата прошлых наблюдений улучшит общий RMSE относительно H69.

Новый механизм: двухступенчатое связывание записей и проверка неоднозначности, а не произвольное снижение точности числового расстояния. Точный ключ State_Factor/building_class/facility_type/floor_area/year_built; ELEVATION остаётся признаком совместимости, но не жёстким идентификатором. Для каждого прошлого года допускается только единственная запись данного ключа; ключи с несколькими записями в одном году не переносятся. Missing year_built остаётся отдельным токеном, не wildcard. Только pastYear<queryYear, ID/target/будущие строки не участвуют в связи. История нескольких строго прошлых лет агрегируется с фиксированной давностью. Неизвестный/неоднозначный профиль возвращает готовый H69/H43.

До регистрации нужно заморозить: (1) точный confidence weight/decay; (2) использование только nearest-past или сводной истории; (3) жёсткий veto при известном изменении рейтинга>фиксированного порога либо штраф; (4) источник совместимого контрольного прогноза и split. Это один кандидат с заранее заданными параметрами, не сетка по outer. Рекомендуемый первый вариант: единственная запись последнего прошлого года, alpha=0.8/(queryYear-lastYear), veto при абсолютном изменении известного rating>20; для точного H69 ключа сохранить существующий H69 prediction. Не подбирать эти константы по outer.

Новизна относительно H69: устраняет ошибку связывания записей через nuisance field, проверяет year-level collisions, отказывается от сомнительных доноров; не просто новый seed/вес существующего exact memory. H63 остаётся read-only аудитом близких X; здесь отдельный регрессионный алгоритм с временной защитой.

Критерии до fit: strict reduction RMSE относительно совместимого сохранённого контроля, отдельный frozen confirmation без выбора по нему;20% — целевой, а не обещанный выигрыш. Анализ: linkage coverage, коллизии, эффективные веса, SSE только для diagnostic train/inner. Лимит900сек; при technical failure статус недостаточно данных. Должны пройти synthetic tests: одинаковый/будущий год исключён, неоднозначность ->fallback, missing не wildcard, permutation инвариантность.

## HYP-071: inverse-score normalized target, direct original-scale loss

Утверждение: нелинейный масштаб энергопотребления, связанный с rating и назначением здания, мешает деревьям различать относительную энергоёмкость в крайнем хвосте; моделирование нормализованной целевой переменной при исходном квадратичном риске исправит эту геометрию.

Механизм: из training-only данных строится положительная монотонно убывающая функция g_facility(rating), представляющая типичный масштаб EUI при данном score. Facility-кривые иерархически shrink к building_class/global curve; редкая/неизвестная facility ->parent. Это эмпирическая кривая, без утверждения о точной формуле ENERGY STAR. Для известного rating z=y/g(rating), обучение регрессора z с sample_weight=g², вывод yhat=g*zhat. Это сохраняет исходный MSE, но меняет разбиение пространства target/параметров; не H12 log(y), не H33 smearing, не H54 аддитивная сумма сплайнов, не H56 второй residual regressor. Для неизвестного rating g=1 и отдельный missing indicator; остальная модель обучается на тех же исходных строках.

До fit заморозить: train-only cross-fitting кривой, допустимую семью (piecewise monotone isotonic с минимальным support), уровни shrinkage, floor/cap g, параметры единственного squared-error booster; не подбирать по старому outer. Для исключения таргетной утечки обучающие z и веса должны получать g из временного OOF, prediction-g из fit-only curve. Альтернатива без target-derived curve — фиксированная normal-score функция, но её физическая обоснованность пока не доказана и fit не разрешён данным draft.

Риск: rating наблюдается лишь у части хвоста; нормализация не создаёт отсутствующую информацию, ошибка g может усиливать хвост. Гарантии20% нет. H71 вторична H70 по ожидаемому отношению сложности к информации, её запуск зависит от SPEC011 и остающегося бюджета. Критерий/бюджет как H70; отдельно проверить отсутствие использования validation y при g, весах, imputation и выборе семейства.
