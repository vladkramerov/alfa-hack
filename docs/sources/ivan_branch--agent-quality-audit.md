## Что установлено и что пока неизвестно

Пользователь сообщил leaderboard `579.658`, время `21:30`, длительность `1084.4` секунды и оценку отставания «в пять раз». Точное название столбца/направление метрики, тип агрегации, результат конкурента, загруженный ZIP/его SHA и платформенные логи здесь отсутствуют. Поэтому нельзя установить причину этого конкретного результата или обещать пятикратный рост.

В [SPEC-001](../specs/SPEC-001-automl-agent.md) по предоставленному PDF зафиксированы нормированные S_reg/S_cls и их средние в диапазоне 0–100 при корректных метриках. `579.658` не соответствует этому диапазону: это может быть другой показатель или обновлённая шкала, но подтверждения нет. Локальные RMSE/Macro F1 и время запуска не позволяют восстановить скрытый leaderboard score. Подтверждение смысла числа и сравнимой версии платформы требуется отдельно; запрос логов организаторам не выполнялся.

Это может расходовать бюджет на несколько полных fit или обрывать медленную финальную модель. Текущее поведение хотя бы сохраняет валидный предыдущий submission; конкретный ущерб на платформе не измерен.

### Проверки правил парсера без обучения

Чистая проверка извлечённого AST-литерала `patterns` и той же fallback-логики дала:

| Контрольное условие | Текущий выбор |
| --- | --- |
| `Regression. Primary metric: MAE. Secondary diagnostic: RMSE.` | `rmse` |
| `Multiclass classification. Primary metric: weighted F1.` | `macro_f1` по fallback |
| `Binary classification. Primary metric: balanced accuracy.` | `accuracy` по совпадению подстроки |

Это проверка правил, без запуска `solution.main`, worker, ML fit или новых публичных гипотез. Она не утверждает, что неизвестные private-задачи используют именно эти формулировки.

## Три минимальных направления исправления

1. **Единый реестр доступных механизмов и совместимой истории.** Подключить root-only XGBoost и обратимое log-target преобразование, выставить их в tool schema/portfolio, импортировать только независимо проверенные совместимые результаты. Политика preprocessing/outliers/target transform должна входить в fingerprint и ключ совместимости scores; full-v1 получает новую историю и не наследует качество старой обработки. При смене policy известные старые fit не повторять ради контроля. Тесты без обучения: сборка/параметры кандидата, mocked worker выбирает сохранённого победителя без evaluate; несовместимый policy-score не используется; label mapping и inverse target round-trip; новый task SHA не получает чужую историю. Это уже относится к интеграции SPEC-005.

2. **Реальный ограниченный исследовательский цикл.** Заменить маленькие жёсткие 4/3 caps на явную deadline-aware политику с отдельным резервом refit и пределами попыток/ошибок/отсутствия прогресса; проверять novelty до запуска, не тратить бюджет на повтор baseline. Поломка одного LLM ответа не должна прекращать оставшиеся заранее разрешённые новые методы. Считать timeout всего HTTP retry-цикла, отправлять валидный компактный JSON с последними результатами и train-only диагностикой вместо обрезки строки. Не расходовать весь лимит только ради числа опытов; иметь явный `stop_reason`. Тесты с fake clock/mocked propose/worker: прекращение по deadline, отсутствие лишних/refit после дедлайна, продолжение разрешённой очереди после API failure, bounded repeated proposals, сохранение лучшего submission и JSON/последних observations. Новых ML fits для этих тестов не требуется.

3. **Явный контракт основной метрики.** Разделить извлечение primary metric/direction/task/output и технический профиль данных; уважать явное указание основной метрики, не выбирать вторичную по порядку regex. Для явно неподдерживаемой/неоднозначной метрики сохранять диагностический исход и применять только обоснованный поддержанный контракт, не выдавая молчаливую замену за правильную. При вероятностном выходе фиксировать positive class и соответствие именованных столбцов `classes_`. Тесты parser/score без fit: три контрпримера выше, оба исходных публичных условия, binary F1/weighted F1, R2 direction, переставленные probability columns и string/int class labels; неоднозначное условие должно давать явный статус.

Ни один пункт не обосновывает повтор HYP-001…020, использование внешних данных или платформенную отправку. Сначала проверяются протокол и новые действительно отличающиеся политики; конкретный вклад в платформенное качество остаётся неизвестен до сравнимой разрешённой проверки.
