# Alfa Hack — первые эксперименты

Данные по умолчанию читаются из соседней папки `../data_for_participants`.
Исходные данные и baseline организаторов не меняются.

## Запуск на Mac

Нужен Python 3.12. Из корня репозитория:

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements-local.txt
python -u first_baseline.py regression
python -u first_baseline.py multiclass
```

Если Python 3.12 установлен как `python3.12`, используй его в первой команде.
Другое расположение данных: `--data-dir /путь/data_for_participants`.

Результаты каждого запуска — в отдельной папке `runs/`: метрики `metrics.json`,
предсказания `submission.csv`, состав обучающей и проверочной частей.
Для классификации также сохраняется `classification_report.txt`.

## Первая проверяемая гипотеза

Линейная модель лучше постоянного прогноза.
Регрессия: Ridge(alpha=1.0), обучение на Year_Factor 1–4, проверка на 5.
Выбран временной split, поскольку test содержит только Year_Factor=6.
Сравнить rmse с dummy_rmse: меньше — лучше.
Классификация: LogisticRegression, stratified 80/20, random_state=42.
Сравнить macro_f1 с dummy_macro_f1: больше — лучше.

Предобработка обучается только на обучающей части. После оценки модель заново
обучается на всём train, формирует CSV для test и проверяет формат результата.
Целевые значения test неизвестны, локальная валидация не равна оценке платформы.
Обычная LinearRegression оказалась численно нестабильной на временном split;
Ridge остаётся линейной моделью и ограничивает величину коэффициентов.

## План команды

Линейная модель → Random Forest → бустинг → Optuna. Сравнивать эксперименты на
одних разделениях; фиксировать гипотезу, параметры, метрику, время и commit.
На текущем этапе меняем один фактор за эксперимент. Сначала воспроизводимость,
затем усложнение. Итог хакатона — универсальный LLM-агент, а этот скрипт служит
учебной отправной точкой, не готовым решением для платформы.

Работать и делать коммиты только в sergey_branch. Самостоятельно ветку не менять.

## Этап 2: проверка Random Forest без API

Гипотеза: случайный лес улучшает RMSE / Macro F1 относительно линейных моделей.
Разделения, seed и предобработка оставлены прежними. Используется 150 деревьев,
max_depth=20, min_samples_leaf=2, max_features=0.8, random_state=42, до 4 потоков.
Веса классов не меняются: проверяем замену семейства модели. Используется
scikit-learn из уже установленного минимального списка; новых библиотек не нужно.

```bash
source .venv/bin/activate
python -u first_baseline.py regression --model forest
python -u first_baseline.py multiclass --model forest
```

Режим `--model linear` воспроизводит первый этап; он остаётся режимом по умолчанию.
Один запуск проверяет одну конфигурацию леса. Результат не доказывает превосходство
любого леса над любой линейной моделью и не заменяет оценку скрытого test.

### Как показать результаты команде

Полные результаты сохраняются в `runs/` и исключены из Git. Для короткого отчёта
передайте папку завершённого запуска (путь берите из вывода скрипта):

```bash
python publish_results.py runs/ИМЯ_ПАПКИ_ЗАПУСКА
```

Команда создаёт JSON-отчёт в `reports/` и обновляет таблицу `reports/README.md`.
Там сохраняются метрики, параметры модели, разделение, время, версии и контрольные
суммы данных. В новых запусках также записываются commit и SHA-256 скрипта.
Затем добавьте отчёты в коммит в sergey_branch и отправьте эту ветку на GitHub.
Логи, секреты и CSV с ответами в отчёт не копируются. API/LLM на этом этапе нет.

## Этап 3: градиентный бустинг CatBoost

Используем разрешённый CatBoost 1.2.8. Первая гипотеза: CatBoost улучшит метрики
случайного леса при прежних split, seed и предобработке. Одна фиксированная
конфигурация: 500 итераций, depth=6, learning_rate=0.05, l2_leaf_reg=3,
random_seed=42, thread_count=4. Для регрессии loss=RMSE, для классификации MultiClass.
Без подбора параметров, ранней остановки и изменения весов классов.

```bash
source .venv/bin/activate
python -m pip install -r requirements-boosting.txt
python -u first_baseline.py regression --model boosting
python -u first_baseline.py multiclass --model boosting
```

Категории пока кодируются прежним OneHotEncoder; встроенное кодирование категорий
CatBoost будет отдельной гипотезой. Выборки валидации не меняются. CatBoost выводит
каждые 100 итераций ошибку на обучающих данных (learn); это не результат валидации.
Сравнивать следует итоговые rmse / macro_f1 из metrics.json.

Полные результаты сохраняются в runs/, короткие отчёты добавляются командой
publish_results.py, как на предыдущем этапе. Линейные модели и лес остаются доступны
без установки CatBoost. LLM и API не используются.

Документация библиотеки: https://catboost.ai/docs/en/concepts/python-quickstart
Параметры: https://catboost.ai/docs/en/references/training-parameters/

## Этап 4: ограниченный подбор параметров Optuna

Optuna 4.2.1 — версия из списка организаторов. Подбираем CatBoost для регрессии
и Random Forest для классификации, сохраняя обработку признаков.
Параметры выбираются по внутренней валидации, без использования основной
проверочной выборки в objective Optuna:

- Регрессия: внутри train годы 1–3 → 4; итоговое сравнение по прежнему году 5.
- Классификация: прежние 80% делятся на 75/25; исходные 20% остаются для итога.

До 8 попыток на задачу, включая стартовую конфигурацию. TPESampler(seed=42,
n_startup_trials=4), попытки последовательно, каждая модель до 4 потоков.
Поиск ограничен 420 секундами: текущая попытка может завершиться после лимита;
проверка кандидата и финальное обучение выполняются дополнительно.

```bash
source .venv/bin/activate
python -m pip install -r requirements-tuning.txt
python -u tune_models.py regression --trials 8 --timeout 420
python -u tune_models.py multiclass --trials 8 --timeout 420
```

Скрипт фиксирует лучшего внутреннего кандидата до просмотра основной валидации.
Затем сравнивает его с прежними настройками на исходной основной выборке.
Если улучшения нет, для итогового CSV сохраняет прежнюю конфигурацию.
Это не полностью независимый финальный тест: основная validation уже использовалась
для сравнения семейств моделей. Метрики скрытого test по-прежнему неизвестны.

Для воспроизведения сохраняются SQLite-журнал study.sqlite3, trials.csv со всеми
попытками, параметры, id четырёх частей, прогнозы основной validation, метрики и
submission.csv. Для краткого отчёта используйте publish_results.py runs/ИМЯ_ЗАПУСКА;
он также копирует таблицу попыток в reports/. Новые данные и API не используются.

Проверки разделения:

```bash
python -m unittest discover -s tests -v
```

Документация: [Study](https://optuna.readthedocs.io/en/v4.2.1/reference/generated/optuna.study.Study.html),
[TPESampler](https://optuna.readthedocs.io/en/v4.2.1/reference/samplers/generated/optuna.samplers.TPESampler.html).

## Этап 5: последовательная проверка гипотез

```bash
source .venv/bin/activate
python -m unittest discover -s tests -v
python -u hypothesis_suite.py --out runs/hypotheses-20261021-stage5
```

Папка вывода должна быть новой: старые результаты не перезаписываются. Эксперименты
выполняются последовательно, без API. Контрольные модели повторяют прежние настройки
для воспроизводимости и сохранения вероятностей для ансамблей.

1. H1: только class_weight=balanced в Random Forest классификации.
2. H2: нативные категории CatBoost вместо OneHotEncoder, обе задачи. Числовая
   обработка (медиана + масштабирование) и параметры CatBoost сохранены.
3. H3: шесть индикаторов пропусков в регрессии, исходный CatBoost с OneHotEncoder.
4. H4: только нулевой year_built заменён на пропуск, прочее как в контроле CatBoost.
5. H5: четыре отношения трафика/пакетов для исходного леса классификации.
6. H6: равное усреднение исходных леса и CatBoost для каждой задачи. В классификации
   усредняются вероятности, порядок классов явно выровнен. Веса не подбираются.
7. Чувствительность: исходный лидер и сильнейшая новая альтернатива сравниваются
   на другом split. Кандидат фиксируется до просмотра новых результатов.

Основные split не меняются: регрессия годы 1–4 → 5; классификация stratified 80/20,
seed=42. Дополнительные: регрессия 1–3 → 4, классификация seed=2026. Они проверяют
чувствительность, не являются полностью независимым тестом: год 4 уже применялся
во внутреннем подборе Optuna, а случайные split классификации пересекаются.
На дополнительном split выполняется только оценка, без лишнего повторного обучения
на всём train и без нового submission. Все основные эксперименты создают CSV.

Каждый запуск сохраняет JSON с полной конфигурацией, метриками, контрольным запуском,
изменением, временем, commit и SHA-256 данных, id частей, прогнозами validation.
Для классификации сохраняются вероятности и отчёт по классам. Краткие отчёты находятся
в reports/ИМЯ_СЕРИИ/. Для ансамблей отдельно записывается стоимость уже обученных
компонентов: время усреднения нельзя сравнивать со временем полного обучения модели.

### Полная таблица для команды

Главная точка входа — reports/README.md. Полный журнал — reports/EXPERIMENTS.md,
Excel с фильтрами — reports/EXPERIMENTS.xlsx, плоские данные — reports/EXPERIMENTS.csv.
Отдельно отмечаются основная валидация, чувствительность к split, диагностика и повторы.
Все внутренние попытки Optuna сохранены, включая повторившиеся параметры.

```bash
python build_experiment_registry.py
```

Эта команда обновляет Markdown, CSV и JSON из сохранённых источников. Excel — снимок
на дату сборки. publish_results.py также обновляет общий текстовый журнал.
Каждая строка содержит модель, конкретное изменение, основные настройки, split,
измеренные метрики, контроль сравнения, вывод, время, commit и источник. Все параметры
доступны в исходном JSON; в Excel они вынесены на отдельный лист. Старые отсутствующие
метаданные не выдумываются. Ключевые настройки первых линейных моделей восстановлены
по сохранённому коду первого этапа и отмечены соответствующим образом.
